# LLM-Based Threat Intelligence Gathering System: Database Architecture (Hybrid Model)

The Database layer utilizes a **"Polyglot Persistence" (Hybrid)** architecture. It completely separates noisy, informal OSINT data (SQLite) from clean, official cybersecurity frameworks (Neo4j) to ensure high-speed vector searches without graph bloat.

---

## Component 1: The OSINT Ledger (SQLite)

This component acts as the system's **"audit trail"** and daily scratchpad.

### Files

#### `db/schema.sql`

- **Purpose:** Contains the structural blueprint (DDL) for the SQLite database.
- **Lifecycle:** It is *never* modified during the daily OSINT gathering pipeline. It is only read and executed by `sqlite_manager.py` during the very first system boot to create the empty tables.

#### `db/sqlite_manager.py`

- **Purpose:** The control center for the relational database. It initializes the `.db` file, manages safe connection pooling, and provides the functions to insert/retrieve data. All entity insertion functions accept keyword arguments (`source_id`, `entity_type`, `entity_value`) matching how `entity_extractor.py` and `ner_spacy.py` call them.
- **Lifecycle:** Called at system boot to initialize the database, and called continuously throughout Phases 1, 3, and 5 to save daily OSINT data.

### Tables & Their Lifecycles

#### Table: `raw_items`

- **What it stores:** The raw text posts from RSS, Reddit, NVD, and AlienVault OTX.
- **When it is called:**
  - **INSERTED** during Phase 1 by the `collectors/` scripts via `sqlite_manager.insert_raw_item()`.
  - **READ** during Phase 2 by `preprocessor/pipeline.py` to get the text ready for the LLM.

#### Table: `entities`

- **What it stores:** "Hard IOCs" (IPs, Hashes, CVE IDs, Domains) extracted by regex, and "Soft Entities" (Threat Actors, Malware families) extracted by spaCy NER.
- **When it is called:**
  - **INSERTED** during Phase 3 by `entity_extractor.py` (regex) and `ner_spacy.py` (spaCy), both calling `sqlite_manager.insert_entity()` directly.
  - **READ** during Phase 5 by `report_generator.py` so the LLM can include the attackers/malware in the final summary.

#### Table: `reports`

- **What it stores:** The final, synthesized executive summary generated by Llama 3, along with a Human-in-the-Loop review status.
- **When it is called:**
  - **INSERTED** during Phase 5 by `report_generator.py` at the very end of the pipeline.
  - **READ** by the CLI (`cli/review_gate.py`) for analyst review and approval/rejection.

#### The schema.sql:
```sql
-- ==============================================================================
-- Database Schema for LLM-Based Threat Intelligence Gathering System
-- ==============================================================================

-- 1. Table for storing raw scraped data from collectors (NVD, OTX, RSS)
CREATE TABLE IF NOT EXISTS raw_items (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    source TEXT NOT NULL,               -- Source name (e.g., 'NVD', 'AlienVault')
    title TEXT,                         -- Title of the article/threat
    description TEXT,                   -- Main content or summary
    source_url TEXT,                    -- Original URL
    published_date TEXT,                -- Publication date
    collected_at TEXT NOT NULL,         -- UTC timestamp of collection
    processed INTEGER DEFAULT 0,        -- 0 = Unprocessed, 1 = Cleaned & Encapsulated
    raw TEXT,                           -- Full raw JSON or HTML (stored as string)
    dedup_key TEXT UNIQUE               -- Unique hash to prevent duplicate entries
);

-- 2. Table for storing hard technical indicators (Extracted by Regex & spaCy)
CREATE TABLE IF NOT EXISTS entities (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    source_id INTEGER NOT NULL,         -- Links to raw_items.id
    entity_type TEXT NOT NULL,          -- 'CVE', 'IPv4', 'Domain', 'Threat_Actor', etc.
    entity_value TEXT NOT NULL,         -- The actual extracted value
    UNIQUE(source_id, entity_type, entity_value),
    FOREIGN KEY (source_id) REFERENCES raw_items(id) ON DELETE CASCADE
);

-- 3. Table for storing final AI reports and Human-in-the-Loop statuses
CREATE TABLE IF NOT EXISTS reports (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    source_id INTEGER NOT NULL,         -- Links to raw_items.id
    summary TEXT,                       -- LLM generated executive summary
    status TEXT DEFAULT 'pending',      -- HITL status: 'pending', 'approved', 'rejected'
    created_at TEXT NOT NULL,           -- UTC timestamp of report generation
    UNIQUE(source_id),
    FOREIGN KEY (source_id) REFERENCES raw_items(id) ON DELETE CASCADE
);
```

## Component 2: The Knowledge Engine (Neo4j Graph + Vector DB)

This component acts as the system's **"long-term strategic memory"** and analysis engine.

### Files

#### `db/neo4j_manager.py`

- **Purpose:** Manages the connection to the local Neo4j Desktop instance (`neo4j://127.0.0.1:7687`). It opens/closes database sessions safely and provides the conduit to execute graph queries.
- **Lifecycle:** Called by Phase 0 scripts to build the graph, and called by Phase 4 (`kg_engine.py`) to search the graph.

### Graph Deep-Dive

#### 1. What objects are stored in the graph?

The graph **strictly** stores official, baseline infrastructure data. It does **not** store OSINT Threat Actors or raw posts.

- **Nodes:** `[CVE]`, `[MITRE_TTP]`, `[Software]`
- **Node Properties:** Each CVE and TTP node contains an `embedding` property — a 384-dimensional mathematical vector representing its technical description, generated by the `all-MiniLM-L6-v2` sentence transformer model.
- **Edges (Relationships):**
  - `(CVE) -[:AFFECTS]-> (Software)` — built from NVD CPE configuration data
  - `(CVE) -[:EXPLOITS_TECHNIQUE]-> (MITRE_TTP)` — built from the CTID CVE→ATT&CK mapping dataset
  - `(MITRE_TTP) -[:TARGETS]-> (Software)` — built from MITRE ATT&CK platform data

#### 2. Why do we need this graph?

- **Reason 1 — Hallucination-Free Mapping:** By converting hacker slang to a vector and searching the graph mathematically, the system guarantees 100% real, official MITRE/CVE mappings, completely bypassing LLM hallucinations.
- **Reason 2 — Blast Radius Prediction:** The graph traverses three hops simultaneously to find all software at risk: CVE→Software directly, CVE→MITRE→Software, and MITRE→Software. This multi-hop traversal is impossible in a relational database.

#### 3. How is the graph built?

The graph is **not** built during the daily OSINT pipeline. It is built by dedicated "Baseline Initialization" scripts run once during first-time setup, in this order:

| Step | Script | Purpose |
|---|---|---|
| 1 | `collectors/sync_mitre_baseline.py` | Downloads MITRE ATT&CK STIX feed, embeds TTP descriptions, creates vector index |
| 2 | `collectors/sync_nvd_baseline.py` | Downloads NVD CVEs year-by-year (1999→present), embeds descriptions, builds AFFECTS and EXPLOITS_TECHNIQUE edges |

`sync_nvd_baseline.py` includes a **checkpoint system** (`data/nvd_sync_state.json`) that saves progress after every year, allowing safe interruption and resumption. Failed years are recorded separately for targeted retry via `--retry` flag.

The CTID (Center for Threat-Informed Defense) public CVE→ATT&CK mapping CSV is used to build `EXPLOITS_TECHNIQUE` edges, since the NVD API only maps CVEs to CWE weakness IDs — not to MITRE TTPs directly.

The vector index (`threat_embeddings_index`) is created automatically at the end of `sync_mitre_baseline.py` using Neo4j's vector index API with 384 dimensions and cosine similarity.

#### 4. How is the graph kept updated?

`collectors/backfiller.py` runs periodically (e.g. weekly) to keep both sides of the graph current:

- **Task 1 — NVD Sliding Window:** Fetches CVEs from the last 30 days and merges them into the graph with updated AFFECTS and EXPLOITS_TECHNIQUE edges.
- **Task 2 — MITRE Re-Sync:** Re-downloads the full MITRE STIX feed and merges any new or updated techniques. Existing nodes are updated in place via `MERGE + SET`.

#### 5. What stage does the graph participate in?

The graph is strictly queried during **Phase 4 (Semantic Vector Search & Graph Traversal)**.

`enrichment/kg_engine.py` receives clean technical behavior sentences from Phase 3, converts each to a vector using `all-MiniLM-L6-v2`, and queries the graph:

> *"Return all CVEs/TTPs where Cosine Similarity to this vector is >= 80%, then traverse all connected Software nodes across three hop paths."*

If no match meets the 80% threshold, the behavior is flagged as a potential **Zero-Day or Novel Technique**. Results are handed off to Phase 5.

## Component 3: The Query Repository

### `db/queries.py`

- **Purpose:** Acts as a centralized dictionary for all database queries. It stores raw SQL strings (`INSERT`, `SELECT`) and Cypher query strings (`MATCH`, `MERGE`) as text constants only — it contains no executable functions.
- **Lifecycle:** Imported as a utility module into `sqlite_manager.py` and `neo4j_manager.py`. Those files own the connection logic and pull query strings from this file, keeping business logic clean and queries easy to audit in one place.
