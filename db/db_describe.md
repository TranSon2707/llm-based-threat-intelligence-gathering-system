# LLM-Based Threat Intelligence Gathering System: Database Architecture (Hybrid Model)

The Database layer utilizes a **"Polyglot Persistence" (Hybrid)** architecture. It completely separates noisy, informal OSINT data (SQLite) from clean, official cybersecurity frameworks (Neo4j) to ensure high-speed vector searches without graph bloat.

## Component 1: The OSINT Ledger (SQLite)

This component acts as the system's **"audit trail"** and daily scratchpad.

### Files

#### `db/schema.sql`

- **Purpose:** Contains the structural blueprint (DDL) for the SQLite database.
- **Lifecycle:** It is *never* modified during the daily OSINT gathering pipeline. It is only read and executed by `sqlite_manager.py` during the very first system boot to create the empty tables.

#### `db/sqlite_manager.py`

- **Purpose:** The control center for the relational database. It initializes the `.db` file, manages safe connection pooling, and provides the functions to insert/retrieve data.
- **Lifecycle:** Called at system boot to initialize the database, and called continuously throughout Phases 1, 3, and 5 to save daily OSINT data.

### Tables & Their Lifecycles

#### Table: `raw_items`

- **What it stores:** The raw text posts from RSS, Reddit,...
- **When it is called:**
  - **INSERTED** during Phase 1 by the `collectors/` scripts.
  - **READ** during Phase 2 by `preprocessor/pipeline.py` to get the text ready for the LLM.

#### Table: `entities`

- **What it stores:** "Hard IOCs" (IPs, Hashes) and "Soft Entities" (Threat Actors, Malware).
- **When it is called:**
  - **INSERTED** during Phase 3 by `entity_extractor.py` and the LLM.
  - **READ** during Phase 5 by `report_generator.py` so the LLM can include the attackers/malware in the final summary.

#### Table: `reports`

- **What it stores:** The final, synthesized executive summary generated by Llama 3, along with a Zero-Day flag.
- **When it is called:**
  - **INSERTED** during Phase 5 by `report_generator.py` at the very end of the pipeline.
#### the schema.sql:
```bash
-- ==============================================================================
-- Database Schema for LLM-Based Threat Intelligence Gathering System
-- ==============================================================================

-- 1. Table for storing raw scraped data from collectors (NVD, OTX, RSS)
CREATE TABLE IF NOT EXISTS raw_items (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    source TEXT NOT NULL,               -- Source name (e.g., 'NVD', 'AlienVault')
    title TEXT,                         -- Title of the article/threat
    description TEXT,                   -- Main content or summary
    source_url TEXT,                    -- Original URL
    published_date TEXT,                -- Publication date
    collected_at TEXT NOT NULL,         -- UTC timestamp of collection
    processed INTEGER DEFAULT 0,        -- 0 = Unprocessed, 1 = Cleaned & Encapsulated
    raw TEXT,                           -- Full raw JSON or HTML (stored as string)
    dedup_key TEXT UNIQUE               -- Unique hash to prevent duplicate entries
);

-- 2. Table for storing hard technical indicators (Extracted by Regex & spaCy)
CREATE TABLE IF NOT EXISTS entities (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    source_id INTEGER NOT NULL,         -- Links to raw_items.id
    entity_type TEXT NOT NULL,          -- 'CVE', 'IPv4', 'Domain', 'Threat_Actor', etc.
    entity_value TEXT NOT NULL,         -- The actual extracted value
    UNIQUE(source_id, entity_type, entity_value),
    FOREIGN KEY (source_id) REFERENCES raw_items(id) ON DELETE CASCADE
);

-- 3. Table for storing final AI reports and Human-in-the-Loop statuses
CREATE TABLE IF NOT EXISTS reports (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    source_id INTEGER NOT NULL,         -- Links to raw_items.id
    summary TEXT,                       -- LLM generated executive summary
    status TEXT DEFAULT 'pending',      -- HITL status: 'pending', 'approved', 'rejected'
    created_at TEXT NOT NULL,           -- UTC timestamp of report generation
    UNIQUE(source_id)
    FOREIGN KEY (source_id) REFERENCES raw_items(id) ON DELETE CASCADE
);

## Component 2: The Knowledge Engine (Neo4j Graph + Vector DB)

This component acts as the system's **"long-term strategic memory"** and analysis engine.

### Files

#### `db/neo4j_manager.py`

- **Purpose:** Manages the connection to your local Neo4j Desktop instance (`bolt://localhost:7687`). It opens/closes database sessions safely and provides the conduit to execute graph queries.
- **Lifecycle:** Called by Phase 0 scripts to build the graph, and called by Phase 4 (`kg_engine.py`) to search the graph.

### Graph Deep-Dive

#### 1. What objects are stored in the graph?

The graph **strictly** stores official, baseline infrastructure data. It does **not** store OSINT Threat Actors or raw posts.

- **Nodes:** `[CVE]`, `[MITRE_TTP]`, `[Software/System]`
- **Node Properties:** Each CVE and TTP node contains an `embedding` property — a 384-dimensional mathematical vector representing its technical description.
- **Edges (Relationships):** e.g., `(CVE) -[AFFECTS]-> (Software)`

#### 2. Why do we need this graph?

- **Reason 1 — Hallucination-Free Mapping:** By converting hacker slang to a vector and searching the graph mathematically, the system guarantees 100% real, official MITRE/CVE mappings, completely bypassing LLM hallucinations.
- **Reason 2 — Blast Radius Prediction:** If a vector search matches a specific CVE, relational tables struggle to find all interconnected systems. The graph instantly traverses the `-[AFFECTS]->` edges to warn the analyst about exactly which software in their enterprise is at risk.

#### 3. How is the graph built?

The graph is **not** built during the daily OSINT pipeline. It is built by dedicated "Baseline Initialization" scripts living in the `collectors/` folder.

| Script | Purpose |
|---|---|
| `collectors/sync_mitre_baseline.py` | Downloads and syncs the MITRE ATT&CK baseline |
| `collectors/sync_nvd_baseline.py` | Downloads and syncs the NVD CVE feed |

These scripts are run **once** to download the JSON feeds, pass their descriptions through the local Sentence-Transformer model to create vectors, and push the Nodes/Edges into Neo4j. Afterward, they only run periodically to fetch updates.

#### 4. What stage does the graph participate in?

The graph is strictly queried during **Stage 4 (Semantic Vector Search & Graph Traversal)**.

`enrichment/kg_engine.py` receives a clean technical behavior sentence from Phase 3, converts it to a vector, and uses `db/neo4j_manager.py` to query the graph:

> *"Return all CVEs/TTPs where the Cosine Similarity to this vector is >= 80%, and return all Software connected to those CVEs."*

The results are then handed off to Phase 5.

## Component 3: The Query Repository

### `db/queries.py`

- **Purpose:** Acts as a centralized dictionary for all database queries. It stores raw SQL strings (`INSERT`, `SELECT`) and Cypher query strings (`MATCH`, `MERGE`) as text constants.
- **Lifecycle:** Imported as a utility file into `sqlite_manager.py` and `kg_engine.py`. Whenever those files need to query their respective databases, they pull the exact query string from this file, keeping the Python logic clean and modular.
